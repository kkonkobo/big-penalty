# Generic ATS send safety

- **Dry run never submits an application.** The service loads the public posting without candidate data and keeps it online through the guarded Apply navigation. It may reject nonessential cookies, navigate to a verified ATS entry URL, or activate one posting-scoped control. The sole non-GET/HEAD exception is a Talentsoft navigation POST tied to the initial posting: the guard matches the actual top-level request's destination and body against the scanned system fields, rejects candidate fields, and never replays a POST redirect. Other writes are blocked; a foreign write attempt ends discovery. The context goes offline before inspecting the landing form. No candidate values, files, credentials, answers, or final submit clicks reach the page. Seeing a form does not validate its widgets or multistep flow. Browser routing alone is not a network sandbox.
- **Generic unattended sending requires approval and a guarded browser.** UI events can transmit data well before the final click. The shared legacy callbacks do not authorize dispatch, and the production ATS adapter registry is still empty.
- **Ambiguity stays durable.** Possible transmissions without a correlated receipt retain a hold for operator verification. Page text on its own and a planner's `submitted` status cannot mark an application sent. Existing operator settlement is unchanged.

To enable a send for a particular ATS, a vetted adapter must establish which operations can transmit data and reserve the attempt durably before any such operation. It must recheck current approval and policy at that boundary, bind the current revision and exact PDF bytes and verified destination to the reservation, and authenticate and correlate the server receipt to the same attempt. Retry is unsafe without conclusive non-delivery or a verified idempotency mechanism. Page text, form structure, and URL changes are not receipts.

The shared form tests exercise the planner, field guards, and navigation against isolated fixtures. Legacy autofill rehearsals cannot be entered through the public dry-run API. The fixture adapter checks the bound PDF bytes and correlates a first-party response to the attempt nonce. Generic tests use the production Patchright pool, with fictional loopback receivers. The sibling-host fixture maps guarded synthetic HTTPS requests to loopback at the transport boundary; it does not use DNS or contact those hosts.

## Autonomous generic applications

- Daily dispatch (when `JOBHUNT_APPLY_AUTO` is enabled), individual **Envoyer**, and batch dispatch can send an already approved generic application. The automatic pass also auto-approves a generic draft at or above `JOBHUNT_APPLY_AUTO_MIN_SCORE` when its CV passes the usual approval checks (verifier, no blocking error); individual and batch **Envoyer** do not approve generic drafts. The browser follows `JOBHUNT_HEADLESS` by default. `JOBHUNT_APPLY_AUTONOMOUS=0` (also `false`, `no`, `off`) disables the generic path (settings are read once per process: restart the web app and let the next daily run start after changing it), and `JOBHUNT_APPLY_DAILY_CAP` defaults to 40 unattended reservations per Paris day per profile, including user-launched generic runs. Two consecutive ambiguous or failed generic reservations pause that host for supervised handling.
- The reservation fixes the approved revision, PDF hash, minimized verified URL, and dedupe identity before the browser opens. Policy and the active reservation are checked before mutations and network writes. Fields outside the bound top-level document or with a mismatched action are left manual. A redirect or navigation that names another employer or posting stops the run (see *Autonomous recipient policy* below). A landing on a recognized ATS is bound as the recipient only before any candidate data is entered, and only when nothing contradicts the posting.
- On the offer page, job-search filters are not application fields. Before any candidate mutation, the engine may activate one visible, unambiguous apply control after rechecking the source URL and document. It admits at most one new tab. A cross-domain landing is accepted on a recognized ATS unless a requisition contradicts the posting. Numbers in a career-site URL are the site's own references and are not compared with the ATS requisition; a requisition from the reservation, the resolved origin or the posting's structured data is compared. The accepted landing document and recipient are bound before fill, and the landing is checked against held and confirmed reservations. If verified origin metadata already supplies a canonical ATS apply URL tied to that offer, the reservation starts there instead. A noncanonical record uses job-ID dedupe and still checks for real potential duplicates.
- The transport guard allows writes on the reserved origin and HTTPS sibling hosts under the same registrable domain (bundled offline Public Suffix List including private domains). It also allows upload and API hosts of the bound recipient's own ATS vendor. Once candidate data has been entered, writes outside an authorized click are limited to recognized upload endpoints carrying the exact approved PDF. During a guarded Next, account or final click, the main document may send one matching native or scripted write. A second write, an out-of-scope recipient or a conflicting posting identifier in a subresource request is **aborted**; the attempt continues, and if the site needed that request it fails on its own. Next rechecks approval and posting identity at each click; the flow stops after at most 12 steps. Sites that need multiple separate writes for one click still end without a receipt and are held.
- Voluntary demographic questions use an explicit opt-out when available, otherwise a required question goes to manual input. The only disclosure added here is the optional standing `race_ethnicity` fact for an identified race or ethnicity question with one equivalent, enabled live option. The engine checks the full option set and wording in the same browser operation as the write, omits the stored fact from planner inputs, and records a fixed selection label rather than the disclosed value in the run's filled-field record.
- `submitted` requires the guarded final write to return 2xx and either positive document text, a known same-origin receipt URL, or a positive JSON response on that exact fetch/XHR request. Only the engine's `confirmation_json` diagnostic is stored, not the response body or its ID. Generic attribution is limited to the single write admitted during the final click; it is not an ATS attestation. A validated same-origin receipt lookup after a native 301/302/303 is a GET only. HTTP success alone, document replacement, and a disappearing button are insufficient. Unsupported submit widgets, unknown destinations and CAPTCHA may require a human; email/OTP verification requires email handling. Potential delivery without a receipt remains **À vérifier** and is never retried automatically.
- This is a browser-level control, not a network sandbox or a guarantee about what an approved employer does server-side. It does not prove the organizational owner of a domain or replace the per-ATS receipt contract. No live ATS has been tested.

## Autonomous recipient policy

This policy applies to unattended generic sends. It is built on four protections: candidate data never goes to a third party or to the wrong employer, no application is sent twice, no hard fact is invented, and an uncertain send is never retried. Everything else proceeds. Dry inspection and the supervised window keep the fail-closed rules described elsewhere in this report. The vetted adapter path (Workday, SmartRecruiters) keeps its declared top-level flow and only gains rule 1.

1. **Unauthorized subresource traffic is aborted and the run continues.** Fetch, XHR, beacon, iframe and other-tab requests to an unapproved destination are aborted, as are their unauthorized redirect or 403/429 responses. The window is no longer closed for them. An aborted request can only prevent a leak. If the form needed it, the run fails on its own and is reported as before. The result records the aborted hosts (`dispatch_diagnostics.aborted_hosts`, at most 20, hosts only, never paths or bodies) and `aborted_requests`.
2. **Before any candidate data is entered** (no value, file or credential typed yet), top-level navigations and redirects to the same registrable domain or to a recognized ATS are allowed. Same-registrable-domain writes are allowed too, including the recipient's ATS infrastructure. They cannot carry candidate data and do not count as a possible transmission. A 403/429 document is shown, and the challenge checks decide. Before the first input, the recipient is rebound to the final landing. A landing on a new registrable domain is reserved durably once by continuity (`bind_apply_landing`, with its duplicate check). Later landings must stay on it. A top-level navigation to an unrecognized foreign site is aborted, or refused when it is the initial redirect: that site is never bound, so no candidate data can reach it.
3. **Career site to recognized ATS.** Hosts that `origin.ats_of_host` / `classify_ats` know (myworkdayjobs, talent-soft, smartrecruiters, teamtailor, talentview, profils.org…) are reachable from the posting. This also applies to an apply link discovered on the verified posting page. They are refused only on evidence of another employer or posting: another tenant or requisition on the bound ATS, a requisition that the verified origin metadata contradicts, or only different posting identifiers on the same site.
4. **After candidate data is entered**, writes go only to the bound recipient's registrable domain and its ATS vendor's infrastructure, under the existing click, upload and posting checks. Everything else is aborted. Top-level navigations that no click admitted are aborted, unless they show evidence of another posting, which still refuses. The final submit keeps its strict checks (single admitted write, receipt rules). Dedupe, reservations and receipt rules are unchanged. A possible transmission without a receipt is still held and never retried.

Pauses are labelled by diagnostic code: *destination* (`recipient_refused_*`), *lien de candidature* (`apply_target_unverified`, `job_page_no_apply_control`, `posting_mismatch`…), *anti-robot* (`challenge_or_rate_limited`), *CAPTCHA* (real CAPTCHA only), *compte*, or *intervention*. A paused run is no longer labelled CAPTCHA by default.

Limits: this remains a browser-level control. Rebinding by continuity trusts that a recognized ATS reached from the verified posting, with no contradicting identifier, belongs to the same employer. An ATS URL without any identifier cannot be checked further. The fixtures use synthetic `.test` hosts registered as an ATS for the test and mapped to loopback; no live site has been tested with this policy.

## Supervised sending extension

A single explicit supervised launch is allowed on an unadapted site after human approval of the exact eligible revision. CLI `big-penalty apply supervised ID` and the application page explain that **typing, upload and blur events can transmit candidate data before any submit click**. Dry inspection remains offline before form inspection and does not interact with controls.

1. Match the displayed revision and destination, re-check approval, eligibility and policy, then reserve the attempt before opening a fresh, visible browser. Store the revision, exact PDF SHA-256 and verified URL/host; upload only the already-hashed byte buffer.
2. An unadapted site opens without candidate data entered. In Envois, choose **Remplir cette étape** (or run `big-penalty apply fill-step APP_ID`) and confirm that the window shows the reserved offer. The preview shows the approved and current destinations in minimized form and warns if neither title nor visible heading matches meaningful words in the job or employer name. Confirmation is bound to the live document in Patchright's isolated world. Reload, replacement, main-frame history navigation (even to the same URL), or a changed URL, title or visible H1 requires a new confirmation. A canonical adapter may fill on launch, but must resolve the live top-level URL, field frame and effective form action to the reserved tenant and requisition before every write. A mismatch closes the window.
3. The planner and verifier fill only the current page. The service rechecks the active reservation, approval, job, policy, PDF and live posting identity before scanning, after reads and before every mutation. Scoped options and the no-auto-consent rule still apply. Autofill is limited to native text and select fields and native CV inputs. The operator handles navigation, custom widgets, consent and the final click. Each additional fill uses the same open window and reservation; it never clicks **Suivant**, **Enregistrer** or **Envoyer**. Missing questions are captured even when the operator must finish by hand.
4. The open page displays French instructions. Close or crash leaves the reserved attempt in **À vérifier**. Page text never settles it. After checking the company's site, use **Envoyée** or **Pas envoyée** on the attempt page. In doubt, leave it held. There is no automatic retry.

Limits: the browser can disappear after transmitting data, so even failures with no recorded click are held. A same-origin endpoint can relay data server-side. The operator may need to finish multi-page forms manually. The fake adapter exercises the shared contract on a local fixture; no production ATS is configured or validated. See `docs/ats-adapters.md`.

## Follow-up controls

- Dry inspection sends field labels/types and opaque references, plus fact keys/types, to the existing configured planner. It omits values, free page text, job metadata and history, and never asks the answer verifier. Value-dependent actions remain non testées. Structured calls use the first enabled provider only when `JOBHUNT_CV_ALLOW_FAILOVER=0`.
- Before opening the supervised window the service reserves the exact approved revision, the SHA-256 of immutable PDF bytes, and a digest of the verified destination. A context-wide guard blocks foreign writes, foreign document navigations, unapproved resources and 403/429. Initial top-level GET/HEAD navigation may follow up to five independently checked redirects; write redirects are never followed. Before any document scripts run, the context disables WebSocket, WebTransport, WebRTC and worker constructors and blocks off-origin EventSource. Service workers remain blocked. Sites that need these transports may not work in the supervised window. No additional Chromium/CDP WebSocket network block is relied on; the init script is not a network sandbox for arbitrary native browser behavior.
- Each field is live-scanned, then the approval, job, reservation and PDF are rechecked after the last read before filling or rolling back. On generic sites, only fields in the confirmed top-level document are eligible. An explicit form action must be same-origin and either have the same path or preserve the posting identifiers without adding another. Missing, empty or `#` actions are allowed. Fields outside that policy are marked **à remplir à la main** and other eligible fields can still be filled. Typing, change/blur and upload events may transmit data at the approved recipient. The final click is manual. A refusal closes the supervised window without handoff; the attempt stays held. The portal’s manual link opens the operator’s own browser, outside these controls. The operator is responsible for checking the recipient and settling the attempt. This manual path is accepted by policy; nothing retries automatically.
- Canonical tenant/requisition metadata is used when available. A canonical match is a hard duplicate. A fuzzy company/title match, including a legacy attempt, needs a manual confirmation for both exact application IDs and their posting fingerprints. The reservation transaction recomputes both fingerprints.
- Application navigation URLs omit fragments and tracking parameters. Unknown query parameters block navigation. Final failed and blocked results retain an allowlisted diagnostic code, fixed French message and at most origin or host context. They discard page text and step details, including running progress, so a later operator settlement cannot recover inferred answers from those failures. Other persisted URLs retain only the origin and recognized numeric posting IDs. Full-page screenshots require `JOBHUNT_APPLY_LOCAL_SCREENSHOTS=1` and are exposed only through existing local evidence routes. Opt-in screenshots can still show private data and should not be shared.
- Daily CV preparation may use the configured LLM before a send reservation; this is accepted by policy and distinct from dispatch. An in-process, reviewed adapter is trusted code, not a sandbox. Brokered adapter HTTP is limited to approved PDF or empty payloads at exact declared tenant/requisition endpoints; both positive and negative adapter receipts require matching attestation and correlation.
- The production headful Patchright tests check the real browser pool with fictional loopback receivers. `about:blank`, `srcdoc` and dynamically navigated frames cannot recover WebSocket through `contentWindow`, including immediately after insertion; blob Worker and SharedWorker constructors are blocked. The tests assert zero receiver traffic. This is a browser-level control, **not a network sandbox**. It does not constrain the operator's own browser, native browser activity, or forwarding from an approved origin.
- Unattended sends never guess a degree, a start date / availability or a salary expectation: without a stored answer the field becomes a question. A positive JSON response counts as a receipt only once the page no longer shows the form with an error or new fields to fill (a draft id on step 2 of 3 is not a receipt).

## Apply entry and account gates

- A scoped Apply control can bind a landing without a visible requisition by continuity: one activation from the bound posting document, before candidate input, with a bounded server redirect chain in the same tab or a single popup. The landing must be on the posting's site, a recognized ATS, or the origin the control explicitly names. The reservation records the binding method and landing host; it does not store login redirect parameters. Subsequent visible requisition identifiers and explicit form destinations must agree with the posting. The account redirect path does not replay a write.
- Dry inspection stops at login or registration with `dry_account_gate` and the origin. In a live run, the existing credential callbacks remain scoped to the host and, for Workday, the career-site namespace. Bound account pages may fill identity and credential fields only. Mixed account/CV forms, unverified destinations and challenges stop the flow. Verification is handed off as `needs_email`; it is not attempted by automation. The final application still needs an independent receipt and is never retried after an uncertain submit.
